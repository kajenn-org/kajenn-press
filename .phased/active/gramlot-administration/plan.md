## Objective

Deliver a Gramlot administration interface over the existing filesystem/Storage services and prove it by building kajenn.org with it. An authenticated team can select a site, manage its pages and routes, edit named HTML/Markdown blocks and template/CSS/JS resources, upload a PNG resource, build, inspect private previews and activate or roll back releases. Reuse the upstream editors and native Source/Data/binding/controller contracts, with no application-local editor port or second persistence authority.

Acceptance criterion (owner, 2026-10-23): kajenn.org, the third sibling of gramlot.org and asqueel.org, is built entirely through the administration UI. Its Gramlot template reproduces the structure the two sibling sites share (header with navigation, hero, sections, dark footer) and its CSS uses the Kajenn palette and logo from `/Users/gporcari/Sviluppo/kajenn/kajenn/assets/branding/`. Template, CSS, logo, pages, content and release are created in the browser by an operator; no catalog record of that site is written by scripts, fixtures or direct file access. Deployment and DNS of kajenn.org are outside this plan.

The owner approved the original three-phase plan, its branch, interactive execution in this chat and plan-time contract skeletons on 2026-10-22. On 2026-10-23 the owner approved this four-phase rewrite around the kajenn.org target. Saving the plan authorizes planning artifacts only; implementation begins through execute-phase. ## Decisions shared by all phases

- Organization: keep the selected site visible; site sections are Content, Resources and Publication. Shared Library is a separate scope. Content lists contain content identities and their language variants; resources contain templates, CSS, JavaScript and media. Operational publication records are never exposed through generic editorial record access.
- Interaction: explicit Save creates a revision, no autosave. Dirty navigation, tab close and exit are protected where the browser permits. Buffers remain in session memory; no persistent local browser cache of unpublished content. A refused or uncertain save never discards the buffer or reports success. Retry uses the same idempotency key for the same submitted snapshot.
- Editors: HTML uses Jodit, Markdown ProseMirror, sources CodeMirror; Python templates explicitly select Gramlot or HtmlBuilder. Rich/Code/Quick preview share one canonical Data value. Embedded HTML is enabled in Markdown quick preview. Unsupported Markdown structures remain preserved source blocks; visual edits can normalize supported markup. Raw code view remains available.
- Preview: quick editor preview is isolated and informative; build preview is authoritative for publication. DOMPurify and nh3 policies are distinct. Explain filtered/unsupported output through diagnostics without modifying the source. Scripts stay in dedicated trusted resource editors, not editorial HTML.
- Media (rewritten 2026-10-23): images enter the site as PNG resources of the site or library, uploaded through the UI and referenced by templates through the existing exact `resources.<revision_id>.url` Data. The existing bounded PNG verification of the build profile applies; original bytes are preserved. Per-variant media references, JPEG/WebP, Pillow, the catalog picker and block insertion are deferred to a later plan; their earlier contracts are kept under Notes.
- Site pages (added 2026-10-23): templates receive the list of the site's pages in Data (path, title, language), ordered deterministically, so a template can generate navigation and links. In a build the list comes from the candidate's route map; in a saved-page render it comes from the saved routes of the same catalog generation. Menus as editorial records, taxonomies and collections stay in Macro 4.
- Orientation (owner request during Phase 1): keep an authenticated Home in the navigation tree; following the authoring priority correction, open Create page by default when a site is available. Explain site selection, retained tabs, content/language variants, templates and named Data blocks, resources/library, revisions, save/build/preview/publication and authorized LLM commands. Distinguish currently available UI from later editors/publication controls.
- UI composition (owner correction during Phase 1): use the native Gallery IndexPage structure, a top toolbar with site selection and New site, tree navigation and retained scope-bound iframe tabs; content workspace separates language selection, named-block selection and metadata. Resource workspace has source tabs plus read-only Data inspection. A refused conflicting save is reported and keeps the local buffer; base/local/current comparison is deferred. Publication workspace shows candidate, build, preview and active release as distinct states. All operator-facing UI is in English (owner correction), including Home, login, navigation, dialogs, messages and demo content; exact layout is negotiated with each phase's mockup.
- Hosting/authentication: optional admin mounted at `/admin/` on the management origin, with Kajenn session/UserStore authentication and deployment-provided grants. Preview/public origins remain separated as in Macro 2. Do not store permanent API credentials in browser Data. Request-scoped service context may wrap the public adapter `handle(Request)` boundary, must reset in `finally`, and must isolate concurrent requests; no private framework overrides or page-owner identity cache.
- Dependencies: qualify a reproducible upstream artifact containing both the new editor collection and the compatible adapter protocol, including authenticated identity. A local prerelease artifact is acceptable if its exact sources/build and hash are recorded; a mutable editable checkout or version number alone is not release evidence. Add optional admin dependencies in the appropriate optional profile; Pillow is not added in this plan. Select and record versions compatible with the supported Python installations during qualification; never silently upgrade the static worker.
- Capability gaps: if the public framework contract cannot satisfy identity, bindings or lifecycle, preserve a reproducer and stop the affected phase for an upstream dependency. Do not edit sibling repositories, invent a private API, or silently substitute a textarea. Already inspected release branches are evidence, not authorization to merge them.
- Scope: no multi-tenant isolation, CRDT collaboration, taxonomy/menu/review/scheduling implementation, Typst, public component authoring/runtime, automatic media derivatives or Asqueel backend. Also deferred on 2026-10-23: conflict comparison/resolution UI, revision diff/restore UI, per-variant media, JPEG/WebP, deployment and DNS. Those roadmap consumers retain their contracts.

## Planning evidence and dependency boundaries

- The clean baseline is the finalized Macro 2 commit on main; archived plans remain on `codex/filesystem-storage` and `codex/rendering-publication`, not copied into this active plan.
- Read-only inspection found CodeMirror, Jodit and ProseMirror upstream. Ran `node --test tests/code-mirror.test.js tests/html-editor.test.js tests/markdown-editor.test.js` in Gramlot's `js/`: 27 passed. These are focused upstream tests, not an application integration/browser qualification.
- `markdownPreview.allowHtml` exists in source, Python grammar and shipped bundle. The default is false upstream; this application enables it. DOMPurify, sandbox/CSP and source/history preservation were tested. The static renderer already enables HTML with nh3 filtering.
- Gramlot develop and adapter develop are not the same artifacts as the newer release branches. Gramlot `codex/intermediate-tree-release` at `6ba8541` has request identity support but not the new editor source files; adapter `codex/intermediate-gallery-release` at `8574708` is version 0.2.12 with public Adapter/Request. No combined editor-plus-adapter artifact has yet been integration-qualified here.
- Core identity in that inspected release is used by auth evaluation; it is not automatically a service identity available on page methods. Qualify the application's public request-boundary context bridge, including concurrent identities and logout, rather than assuming a page API exists.
- Existing publication services lack discovery for several operational records and effective user/scope capability projections. Add purpose-specific common operations rather than scanning private catalog records from the UI.
- Existing image publication only verifies a bounded PNG profile. JPEG/WebP support changes validation, dependency closure, artifact MIME and serving tests; it is not just an upload extension filter. Pillow format documentation: https://pillow.readthedocs.io/en/stable/handbook/image-file-formats.html . Qualify decoding support in the installed artifact, including WebP availability.
- Existing editor previews and rich widgets do not establish a public catalog-media cursor insertion hook. This plan deliberately specifies explicit end-of-block Data insertion, without private Jodit/ProseMirror engine access.
- Model hints: phases 1 and 2 retain integration/authentication and source/Data contract engineering, hence fable/high. Phase 3 composes the qualified release services and explicit read projections, hence opus/medium. Phase 4 is site authoring and visual comparison, hence opus/high. These are suggestions, not a request to change this chat's model.
